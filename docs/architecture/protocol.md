# WebSocket Protocol v1

Human-readable description. The normative, machine-readable contract is
`protocol/src/main/resources/asyncapi/rts-ws-v1.yaml` (AsyncAPI 3.0) plus golden samples in
`protocol/src/test/resources/golden/` (one file per message type). `GoldenFilesTest` in the `protocol`
module checks that the code encodes each message to its golden file, decodes the file back, and that
the AsyncAPI schema accepts the file. The Kotlin classes, error codes (`WsErrorCodes`) and close codes
(`WsCloseCodes`) are in the same module.

## Endpoints

| Path | Who | Auth | Purpose |
|---|---|---|---|
| `/ws/v1/driver` | Driver SDK | `Authorization: Bearer <token>` (header) or `?token=` (fallback for clients that can't set headers) | Upload fixes and device status; receive ACKs and commands |
| `/ws/v1/guest` | Guest app | same | Subscribe to one trip; receive driver position, progress and events |

Before phase 3 (no auth yet) the driver endpoint accepts a `deviceId` in `Hello`.

## Envelope

Every frame is a JSON text frame holding one message. Polymorphism uses kotlinx.serialization's
class discriminator `"type"`:

```json
{ "type": "fix_batch", "seq": 42, "fixes": [ ... ] }
```

Messages are grouped into two sealed hierarchies in the `protocol` module:

```kotlin
@Serializable sealed interface ClientMessage   // sent by devices
@Serializable sealed interface ServerMessage   // sent by the server
```

Unknown `type` values are rejected with `error{code=UNKNOWN_MESSAGE}` and the session stays open
(forward compatibility: a newer SDK must not be disconnected by an older server).

## Driver session

### Handshake

```
client → hello    { protocolVersion: 1, deviceId, sessionId, lastAckedSeq, sdkVersion }
server → welcome  { sessionId, resumeFromSeq, serverTime, limits: { maxFixesPerBatch, maxFrameBytes, maxMessagesPerSecond } }
```

- `sessionId` is generated by the SDK when tracking starts (UUID) so it survives reconnects.
- The location provider is a field of each fix, not of the session: the SDK can fall back from GMS
  to AOSP while a session runs.
- `resumeFromSeq` = highest seq the server has stored for that session + 1. The client resends
  everything from there. The server's number wins over the client's `lastAckedSeq`.
- No `hello` within 10 s → close `4401 HANDSHAKE_TIMEOUT`.
- `protocolVersion` unsupported → close `4400 UNSUPPORTED_VERSION`.

### Upload

```
client → fix_batch      { seq, fixes: [Fix, ...] }            // 1..maxFixesPerBatch fixes
server → ack            { seq, accepted, rejected: [{index, reason}] }
client → device_status  { at, battery: {...}, gnss: {...}?, motion? }   // phase 4 / 9
```

`Fix`:

```json
{ "lat": 10.7769, "lng": 106.7009, "accuracyM": 8.5,
  "speedMps": 11.2, "speedAccuracyMps": 0.8,
  "bearingDeg": 87.0, "bearingAccuracyDeg": 4.0,
  "altitudeM": 12.0, "verticalAccuracyM": 3.5,
  "recordedAt": "2026-09-30T02:15:04.120Z", "provider": "GMS_FUSED", "mock": false,
  "satellites": { "usedInFix": 14, "meanCn0DbHz": 31.5 } }
```

| Field | Required | Meaning | Android SDK source (`location_sdk`) |
|---|---|---|---|
| `lat`, `lng` | yes | WGS 84 degrees | `LocationReading.latitude`, `.longitude` |
| `accuracyM` | yes | Horizontal accuracy radius in meters (68% confidence) | `accuracyMeters` |
| `speedMps`, `speedAccuracyMps` | no | Meters per second | `speedMetersPerSecond`, `speedAccuracyMetersPerSecond` |
| `bearingDeg`, `bearingAccuracyDeg` | no | Degrees, 0 = north | `bearingDegrees`, `bearingAccuracyDegrees` |
| `altitudeM`, `verticalAccuracyM` | no | Meters | `altitudeMeters`, `verticalAccuracyMeters` |
| `recordedAt` | yes | UTC time at which the device recorded the fix (device clock) | `timeMs` |
| `provider` | no, default `UNKNOWN` | `GMS_FUSED`, `AOSP_GPS`, `AOSP_NETWORK`, `AOSP_FUSED`, `UNKNOWN`; an unknown string decodes to `UNKNOWN` | Needs an SDK change: `LocationReading.provider` is `"fused"` for both GMS and AOSP fused fixes |
| `mock` | no, default `false` | The OS marked the fix as coming from a mock location provider | `isMock` |
| `satellites.usedInFix`, `satellites.meanCn0DbHz` | no (absent for Wi-Fi or cell fixes) | Satellites used in the fix and their mean carrier-to-noise density | Needs an SDK change: `GnssReading` (the latest reading at the time of the fix) is internal today |

A fix with `mock = true` is rejected with reason `MOCK_LOCATION`. It is still part of the ACKed batch.

### ACK semantics

1. The server sends `ack{seq}` **only after the batch is durably stored** (transaction committed).
2. Writes are **idempotent** per `(sessionId, seq)`: a batch whose seq is already stored is not
   stored again, but is ACKed again with the original counts.
3. Rejected fixes (failed validation or filters) are still part of an ACKed batch: `ack` means "the
   server has processed this batch", not "every fix was kept". The client deletes the batch either way.
4. Batches may arrive out of order after a reconnect; the server stores them by seq and does not
   require contiguity. Gaps are reported in telemetry, not treated as errors.
5. The client deletes a batch from its local queue only on receipt of its `ack`.

### Batch numbering (client rules)

The server identifies a batch by `(sessionId, seq)`. Points need no IDs of their own: a point is
identified by `(sessionId, seq, index)`. Retries are safe only if the client follows these rules:

1. `seq` starts at 1 for each `sessionId` and increases by 1 for every new batch.
2. The client assigns `seq` when it writes the batch to its on-disk queue, before the first send.
3. After a batch has a `seq`, its content never changes: no adding, removing, splitting or merging of points.
4. After a reconnect, the client resends the same batch with the same `seq` and the same content.

If the same `seq` arrives again with different content, the server keeps the first copy and ACKs the
original counts. The server does not compare or store the second copy.

```
Phone                                   Server
  │── fix_batch seq=41 ────────────────►│ store (session, 41)
  │◄──────────────────────── ack seq=41 ─│
  │── fix_batch seq=42 ──X  (drop)       │
  │ ...reconnect...                      │
  │── hello lastAckedSeq=41 ───────────►│
  │◄──────────── welcome resumeFrom=42 ──│
  │── fix_batch seq=42 ────────────────►│ store (session, 42)
  │◄──────────────────────── ack seq=42 ─│
```

### Commands (phase 5)

```
server → command      { commandId, kind: "set_constraint" | "register_geofences" | "flush_queue", payload, expiresAt }
client → command_ack  { commandId, status: "applied" | "rejected", reason? }
```

Commands are persisted until acknowledged or expired and re-sent after `welcome` on reconnect.

## Guest session (phase 3+)

```
client → subscribe        { tripId }
server → subscribed       { trip: TripSnapshot }
server → driver_position  { tripId, lat, lng, bearingDeg, speedMps, at }
server → trip_progress    { tripId, remainingM, etaS, basis: "straight_line" | "route" }
server → trip_event       { tripId, event: { type: "arriving" | "arrived" | ... , at, ... } }
server → route_updated    { tripId, polyline, distanceM }                    // phase 7
client → unsubscribe      { tripId }
```

A guest may subscribe only to trips where they are the guest; otherwise `error{code=FORBIDDEN}`.

## Errors and close codes

`server → error { code, message, correlatesTo? }` for recoverable problems; the session stays open.

| Error code | Meaning |
|---|---|
| `MALFORMED_MESSAGE` | The frame is not valid JSON |
| `INVALID_MESSAGE` | Valid JSON with a wrong shape; also a `hello` with an invalid `sessionId` or `deviceId`, and a second `hello` |
| `UNKNOWN_MESSAGE` | A `type` that this server does not know (for example from a newer SDK) |
| `RATE_LIMITED` | More messages per second than `limits.maxMessagesPerSecond`; this message was dropped |
| `EMPTY_BATCH`, `BATCH_TOO_LARGE`, `INVALID_SEQ` | The batch was not stored and gets no ack; `correlatesTo` is its seq |
| `SESSION_DEVICE_MISMATCH` | The `hello` names a session that another device started. Start a new session and send `hello` again |

The constants are in `WsErrorCodes` (protocol errors) and `TrackingError` (business errors) in code, and in
the `Error` schema of the AsyncAPI document.

| Close code | Meaning | Client should |
|---|---|---|
| 1000 | Normal close | Stop |
| 1001 | Server shutting down | Reconnect with backoff |
| 1008 | Policy violation (auth failed mid-session) | Refresh token, reconnect |
| 1009 | Frame too large | Split batches; reconnect |
| 1011 | Internal error | Reconnect with backoff |
| 4400 | Unsupported protocol version | Stop, report |
| 4401 | Handshake timeout / missing hello | Reconnect |
| 4403 | Unauthorized role for endpoint | Stop |

## Keepalive

WebSocket ping every 15 s, timeout 15 s (Ktor `pingPeriod`/`timeout`). A driver with no frames and
no pong for `staleAfter` (default 60 s) is reported `DRIVER_STALE` to guests (phase 4).

## Limits

| Limit | Default | Enforced by |
|---|---|---|
| Max frame size | 64 KiB | Ktor `maxFrameSize` → close 1009 |
| Max fixes per batch | 100 | handler → `error{code=BATCH_TOO_LARGE}`, batch not ACKed |
| Max inbound messages/s per session | 20 | handler token bucket → `error{code=RATE_LIMITED}` |
